# aide共通ルール

> **このファイルはaideフレームワークの共通ルールです。編集しないでください。**
> プロジェクト固有の設定は CLAUDE.md / AGENTS.md に記載してください。

aide（AI Driven for Enterprise）は、IDE / コンソールを扱える層（PM・製品運用者・新規開発者・既存運用者）が、AI と伴走しながら業務を進めるための Enterprise 向けフレームワークである。AI に任せきりにせず、人が AI を乗りこなして業務を前に進める。

## 基本原則（3大原則）

1. **Human-in-the-Loop** — ハーネスエンジニアリングを支える大原則。AIへの**フィードフォワード（インプット＝指示・仕様の精度を上げる）**と**フィードバック（アウトプット＝仕様との照合チェックを徹底する）**の両方向を人間が検査する。実装前の承認ゲートと、完了時のペルソナレビュー（[レビュー規約](#レビューエージェント起動規約)）がこれを体現する。承認なしで反映・実装など不可逆な操作に進まない。
2. **SSoT（Single Source of Truth）** — 仕様駆動開発（SDD）と Spec-Anchored により仕様書を常に最新化し、人もAIも**ドキュメントを正として対話・判断する**。コードは仕様の実装物、テストは仕様の検証物。検討の経緯（ブレスト結論）も文書資産として残す。
3. **伴走性（指定なしでも伴走）** — 指定がなくても、不明確な指示は決め打ちせず確認・ブレストを挟み、意図が固まれば適切なスキルを**提案し、承認を得てから実行する**（[自由モード](#利用モード)）。いきなり実行せず、相談役として現在地を分析・提案する。AIと伴走しながら業務を前に進める。

**3原則の相互補強**: SSoT が HITL のフィードフォワード（良質なインプット）を支え、HITL のフィードバック（アウトプット検査）が Spec-Anchored を通じて SSoT を最新化する。伴走性がこの循環を日々の対話に接続する。

## 運用ルール（作法）

3大原則を具体的に守るための作法。

- **選択式・オンデマンド**: 必要な情報・フェーズ・タスク・成果物を選択肢で提示し、選ばれたものだけ生成する。**勝手にフォルダを作らない**（[選択式オンデマンドフォルダ生成](#選択式オンデマンドフォルダ生成)）
- **浅い階層・中身は自由**: 自動生成するフォルダはフェーズ区分けの1段のみ。中の構成は利用者に委ねる
- **作業フォルダ外に出さない**: 確認・設定した作業フォルダ配下にのみ出力する（[作業フォルダルール](#作業フォルダルール)）
- **インデックス駆動の読み込み**: 履歴は index.md のサマリを見て「関連するもの」だけ読む。全件・最新N件ではなく関連性を基準にする

## 利用モード

aide には2つの利用モードがある。

### 自由モード（init 不要）

何も指定せずに作業指示を出した場合のデフォルト挙動。`aide-init` を実行していなくても機能する。

**作業指示を受領したときのデフォルト手順:**

1. **不明確さの判定**: 指示の目的・対象・成果物が曖昧なら、決め打ちせず「一度ブレストしますか？」と提案する（`aide-brainstorm` を案内）。明確なら次へ進む
   - 対象が**作業フォルダ内に置かれたファイル**（利用者が先に作成した問い合わせ・障害メモ・要件メモ等）を指す場合は、そのファイルを読んで意図・対象を把握してから進む（ファイル先置きフローに対応）
2. **作業フォルダの確認**: 成果物を出力する作業フォルダが未設定なら、必ず場所を確認してから生成する（[作業フォルダルール](#作業フォルダルール)）。確認なしに作業フォルダ外へファイルを作らない
3. **決定・変更の検知**: 会話中に決定事項や仕様変更が生じたら、[反映フロー](#会話ドキュメント反映フロー)に従い反映計画を提示する
4. **スキルの提案と実行**: 意図が確定したら、適切なスキルを**提案し、ユーザーの承認を得てから実行する（いきなり実行しない）**。迷っている場合は現在地（プロファイル・進行状況・成果物の有無）を分析し、1〜3個の候補を理由つきで提示して選ばせる。これらの判断は `aide-advisor`（相談役）が担う。なお自由モードの自動性は本 rules.md が常時ロードされることで保証され、`aide-advisor` は明示起動の入口（迷ったら叩く相談役）も兼ねる。スキル自体が自律的に常駐起動するわけではない

### 伴走モード（init 済み）

`aide-init` でセグメントを選ぶと、そのセグメント向けの伴走が有効になる。

- 選択式で提示されたフェーズ・タスクのうち、選ばれたものだけ浅いフォルダが生成される
- `aide-journey` が伴走タスクを生成し、タスクに沿った進行を支援する
- 利用者がタスク順を先走った場合や、既に決まったことを蒸し返した場合は指摘する（[伴走モデル](#伴走モデルaide-journey)）

## セグメント（対象者区分け）

aide は対象者を4セグメントの1軸で区分する。Enterprise 向けという位置づけは全セグメント共通であり、監査・トレーサビリティ・品質ゲートは「選択式フェーズ/オプション」として ON/OFF する。

| セグメント | 識別子 | 主目的 |
|---|---|---|
| **PM業務** | `pm` | KPI/ゴール設定とプロジェクト管理（役職付き・管理業務中心） |
| **製品運用** | `product` | 製品の設定作業と問題解決（コードを書かない運用） |
| **新規開発** | `dev` | ウォーターフォール×SDD の AI 駆動開発 |
| **既存運用** | `ops` | 既存システムの問い合わせ・課題・障害対応 |

複数セグメントの併用も可能（例: `pm+dev`）。

## プロファイル

伴走モードの設定は **プロファイル** として保持する。

**保持先**: プロジェクトの `CLAUDE.md`（および `AGENTS.md` から参照）。`aide-init` が以下の「## aideプロファイル」セクションを生成・更新する。

```markdown
## aideプロファイル
- セグメント: dev          # pm / product / dev / ops（複数可）
- 作業フォルダ: docs/       # 成果物の出力ルート
- 有効フェーズ: 要件, 基本設計, 詳細設計  # 選択済みフェーズ（オンデマンドで追加）
- 成果物: 要件書 / 基本設計書, ER図 / 詳細設計書  # 選択済み成果物（フェーズ順・カタログから選択）
- オプション: トレーサビリティ            # 監査/トレーサビリティ等の選択式オプション
- スライドテーマ: corporate              # 案件の既定 Marp テーマ名（省略可・既定 corporate）。MD frontmatter の theme で個別上書き可
```

プロファイルが存在しない場合は自由モードとして扱う。

## 作業フォルダルール

- **未設定なら必ず確認**: プロファイルに作業フォルダが無い場合、成果物を生成する前に出力先を確認する
- **作業フォルダ外に作らない**: ブレスト・議事録・成果物などのファイルは、確認・設定された作業フォルダ配下にのみ生成する。一時ファイルや想定外の場所に勝手に出力しない
- **設定の記録**: 確認した作業フォルダはプロファイルに記録し、以降は再確認しない

## 選択式オンデマンドフォルダ生成

- フェーズ・タスクは **選択肢で提示** し、選ばれたものだけフォルダを生成する
- 生成するフォルダは **フェーズ区分けの1段のみ**（深い階層を勝手に作らない）。フォルダ内の構成は利用者の自由
- 作業中に新しいフェーズが必要になったら、その都度選択肢を出して追加生成する
- init 時に全フェーズフォルダを一括生成しない

## 成果物カタログ

「どのフェーズでどの成果物を作るか」「各成果物の章立て」は、利用者・会社が調整できる。

- **カタログ（成果物セット定義）**: `.aide/templates/deliverables-catalog.md`（マニフェスト）に、セグメント×フェーズごとの成果物セットと各成果物のテンプレートパスを定義する。スキル（`aide-init` / `aide-brainstorm` / `aide-dev-spec` 等）はこれを読み、**選択式**で成果物を提示する（既定マーク付き）。利用者は成果物を増減でき、選択結果はプロファイルに記録する
- **テンプレート（章立て）**: 各成果物の雛形を `.aide/templates/deliverables/<name>.md` に持つ。スキルは選択された成果物の雛形を使って生成する
- **会社/プロジェクトのメニュー調整**: `.aide-templates/`（プロジェクト直下・`.aide/` の外）に同名ファイルを置けば、カタログ・雛形ともにそちらが優先される（`.aide/templates/` → `.aide-templates/`）。**`.aide/` 本体は一切編集しない**
  - 利用者に手作業させない。`aide-init` が「標準メニューを調整しますか？」と確認し、Yes の場合に**`.aide-templates/` を自動生成・更新**する（[aide-init](skills/aide-init/SKILL.md) 手順2-2）
  - カタログ・雛形はスキルが**実行時に直接読む**ため、編集すれば**即反映**される。`sync` の再実行は不要（`sync` はスキル/エージェントのラッパー生成専用）
- **このプロジェクトで作る成果物の選択**: メニューを変えずに「今回どれを作るか」を選ぶだけなら、`aide-init` の選択式（プロファイルの「成果物」行に記録）で完結する。ファイル編集は不要
- **成果物の中身の調整**: 生成済み成果物は直接編集してよい（フォルダ内は自由）。会話での修正は[反映フロー](#会話ドキュメント反映フロー)（`aide-sync`）で OK ゲートを通して反映する

### エクスポート/スライドのテンプレート（export 系）

提出用の変換テンプレート（スライド・見積・スケジュール・ディスカッション・汎用ドキュメント）は `.aide/templates/export/` を正本とし、**対象物ごとのフォルダ**（`slide/` `document/` `estimate/` `schedule/` `discussion/`、共通の `metadata.yaml`・`scripts/`）に整理する。

- **二段解決**: deliverables と同様、案件側 `.aide-templates/export/<同じ相対パス>` が優先される（`.aide/templates/export/` → `.aide-templates/export/`）。スキル（`aide-export` / `aide-pm-slide`）は実行時にこの順で読むため**編集即反映**（`sync` 不要）。**`.aide/` 本体は一切編集しない。**
  - HTML テンプレート等の**単一ファイル**は同名で**上書き**（案件側優先）。
  - **スライドテーマは「上書き」ではなく「追加」**: テーマ一覧は `.aide/templates/export/slide/themes/*/` と `.aide-templates/export/slide/themes/*/` の**和集合**。案件側に `themes/<name>/` を足すと選択肢が増え、同名フォルダのときだけ案件側が優先される。
- **スライドテーマ=フォルダ**: `slide/themes/<name>/` に `theme.css`（必須）＋任意で `assets/`（画像・ロゴ）・`rules.md`（テーマ固有の作図ルール）をまとめる。**命名規約はフォルダ名＝CSS 先頭の `@theme` 名＝MD frontmatter の `theme:` 値を一致させる**（既定 `corporate`）。
- **どのテーマを使うかは MD スライドの frontmatter `theme:` で指定**する（Marp 標準キー）。`md2pptx.py` は frontmatter の `theme:` を読み、同名 `theme.css` の `:root`（`--color-*`）をパースして PPTX に同じ配色を反映する（Marp 経路の CSS と PPTX 経路で配色が一致）。
- **案件の既定テーマはプロファイルに記録**できる（[プロファイル](#プロファイル) の「スライドテーマ」行）。`aide-pm-slide` が新規スライドの初期 `theme:` に使い、MD 側の個別指定があればそちらが優先される。

## コンテキスト管理

### 常に読むファイル（セッション開始時）
- CLAUDE.md / AGENTS.md（プロファイルを含む）
- 作業フォルダ直下の課題/タスク管理ファイル（存在すれば）
- 各フェーズフォルダ内の brainstorms/index.md（存在すれば）

### フェーズに応じて読むファイル
- 要件定義作業時 → 要件書
- 設計作業時 → 要件書 + 設計書
- 開発作業時 → 設計書 + 製造計画書
- テスト作業時 → 製造計画書 + テスト仕様書

（具体パスはプロファイルの作業フォルダと有効フェーズに従う。固定パスを前提にしない）

### インデックス経由で読むファイル
- meeting-notes（打合せ） → 最新1-2件のみ
- brainstorms → **まず index.md を読み、今回のテーマに関連するブレストを特定してから読む**。件数制限なし

関連性のない履歴ファイルは読まないこと。

### 会話時の自動グラウンディング

スキル実行時以外の通常会話でも、プロジェクトに関連する話題には文書ベースの裏付けを行う。

#### トリガー判定

該当する場合のみグラウンディングを実行する（一般的なプログラミング知識・雑談はスキップ）。

| 会話中のシグナル | 確認先 |
|---|---|
| 機能名・モジュール名・技術名への言及 | 設計書 + brainstorms/index.md |
| 技術選定の議論 | brainstorms/index.md で過去の選定ブレスト確認 |
| 「なぜこうしたんだっけ」等の過去決定への言及 | brainstorms/index.md → 該当ブレスト |
| 新しいアイデア・代替案の提案 | brainstorms/index.md（過去に検討済みか確認） |
| APIの動作・仕様に関する質問 | 設計書の該当セクション |
| 特定の関数・ファイル・パスへの言及 | 実ファイルの存在確認 |

#### 確認手順（インデックス駆動）

1. 該当フェーズの brainstorms/index.md のテーマ・結論サマリを確認
2. 関連するブレストがあれば結論セクションのみ読む
3. 仕様に関わる話題は該当成果物の関連セクションを確認
4. コードの存在・動作に関する主張は実ファイルで確認してから回答する

#### 出力ルール

- **通常時**: 文書の参照を自然に会話に織り込む（「設計書 §3.2 によると…」）
- **矛盾検出時**: 回答前に警告ブロックを表示する:
  > **過去の決定との不一致を検出しました**
  > [ブレスト日付・結論の要約]
  > 変更する場合は `aide-brainstorm` で検討履歴を残すことを推奨します。
- **該当文書なし**: 通常回答する。決定事項が生まれたら記録を案内する
- **コード参照**: 存在しない関数・ファイル・APIを記憶だけで回答しない

#### 注意事項

- 会話時は必要最小限のみ読む。index.md で関連性を判断してから個別ファイルを読む
- プロジェクト文書が未作成（`aide-init` 未実行等）の場合はスキップする
- ユーザーが「過去の決定は無視して自由に検討したい」と言った場合は、過去決定を参考情報として提示しつつ制約としない

## 会話→ドキュメント反映フロー

AI と会話した内容を元に、必要なドキュメントへ反映する。検知は常時（rules.md）、実施は `aide-sync` に一本化する。

1. **検知**: 会話中に決定・変更・新事実が生じたことを検知する
2. **反映計画の提示**: どのドキュメントのどこを、どう変更するかの **反映計画** を提示する
3. **OK ゲート**: 利用者の OK が出てから実施する。**承認なしにドキュメントを書き換えない**（あくまで提案）
4. **実施**: OK 後に `aide-sync` がドキュメントへ反映する

## 伴走モデル（aide-journey）

- `aide-init` 後、選択されたセグメント・フェーズに沿って **伴走タスク** を生成する
- タスクに沿った進行を支援し、現在地と次アクションを提示する
- **先走り検知**: 利用者が前提条件・依存の未充足なタスクを先に進めようとした場合、または既に決まったことを蒸し返した場合は指摘する
- 進行状況は作業フォルダ内の管理ファイルで一元管理する

## レビューエージェント起動規約

ペルソナ別レビューはサブエージェント定義（`.aide/agents/`）を正本とし、各ツールへ sync で展開する。

- **作業完了時に自動起動**: 各作業の完了時、対応するペルソナエージェントを独立コンテキストで起動しレビューする
- **新規開発の V字モデル照合**:
  - 製造まで → 各フェーズのアウトプットが前フェーズのアウトプットに準拠しているかを照合
  - テストフェーズ → 対応フェーズと照合（要件定義⇔運用テスト / 基本設計⇔結合・システムテスト / 詳細設計（実装計画書）⇔単体テスト）
- **既存運用** → ドキュメントレビュアー / ソースレビュアーが対象を点検
- レビュー結果は指摘事項として提示し、対応要否は利用者が判断する（Human-in-the-Loop）

## カスタマイズ

**`.aide/` はフレームワーク核として一切編集しない（不可侵）。** カスタマイズはすべて `.aide/` の外で行う。

- **正本コア（不可侵）**: `.aide/skills/`・`.aide/agents/`・`.aide/templates/`・`.aide/rules.md`
- **Rules（プロジェクト固有ルール）**: `CLAUDE.md` / `AGENTS.md` に直接記述する（共通 `.aide/rules.md` は編集しない）
- **Skills / レビューエージェント（独自追加）**: 独自スキルは `.claude/skills/`（Claude Code）・`.agents/skills/`（Copilot・Codex）、独自レビューエージェントは `.claude/agents/` に直接作成する。sync は aide 管理外のものを消さない・上書きしない。**既存 `aide-*` スキル／ペルソナの上書き（挙動変更）は行わない**——挙動を変えたい場合は別名で独自に追加する
- **Templates（成果物カタログ・章立て）**: `.aide-templates/`（プロジェクト直下）に上書きを置く。スキルが実行時に `.aide-templates/` を優先して読む（[成果物カタログ](#成果物カタログ)）
- いずれも sync 不要で即反映される（sync はコア正本からのラッパー生成専用）

## セグメント別運用

### PM業務（pm）
- プロジェクトの **KPI / ゴール** を設定し、ゴールから逆算して進める（`aide-pm-charter`）
- スケジュール・課題・メンバなどPMとして必要な管理を行う（`aide-pm-manage`）

### 製品運用（product）
- **製品バージョンを指定** し、WEB検索で適切な情報源から問題解決を図る（`aide-product-resolve`）
- 運用作業がメインのため、課題管理と設定作業記録を行う（`aide-product-task`）

### 新規開発（dev）
- init 後に必要な開発フェーズを選択し、選んだフェーズのフォルダを生成する
- 原則ウォーターフォールの AI 駆動開発。SDD で AI へのインプット精度を上げ、アウトプットを徹底チェックする（ハーネスエンジニアリング）
- 製造まではアウトプットが前フェーズに準拠しているかをチェック。テストフェーズは V字で対応フェーズと照合（[レビューエージェント規約](#レビューエージェント起動規約)）

### 既存運用（ops）
- **課題管理は必須**
- 開発時ドキュメント・ソースを格納するフォルダを用意し、配置されたものを読み取って回答する
- **問い合わせ対応 / 課題対応 / 障害対応** ごとにフォルダを用意する
- レビューはドキュメント・ソースを点検する

## 開発ガイドライン

### コーディング規約
- 仕様を正としてコードを作成する
- テストは仕様書から導出する
- 1PR = 1タスク
- コミットメッセージは Conventional Commits + 関連する仕様（設計書の章番号等）
- セキュリティに関わるコードは慎重にレビュー
- `.env` や認証情報をコードに含めない

### 仕様駆動開発（SDD）ルール
- 仕様（設計書・製造計画書）を正として実装する
- 実装前に対象・方針・影響範囲の確認を取る
- AI生成コードが仕様に準拠しているか必ずレビュー
- 仕様に記載がない点はユーザーに確認してから実装する

### Spec-Anchored（仕様双方向同期）
- **仕様→実装**: 仕様を正として実装する
- **実装→仕様**: 実装中に仕様外の判断を行った場合、[反映フロー](#会話ドキュメント反映フロー)で仕様への反映を提案する
- 差異検出時はユーザーに選択肢を提示する: ①仕様を更新 ②コードを仕様に合わせる ③差異を課題として記録

## プロジェクト管理

### 課題管理（dev / ops / product）
- 課題は作業フォルダ内の課題管理ファイルで一元管理
- 課題ID: I-XXX（連番）
- ステータス: OPEN → IN_PROGRESS → RESOLVED → CLOSED / WONTFIX

### タスク管理（ops）
- タスクは作業フォルダ内のタスク管理ファイルで一元管理
- タスクID: T-XXX（連番）
- ステータス: OPEN → IN_PROGRESS → RESOLVED → CLOSED / WONTFIX

### 決定事項管理
- 決定事項は brainstorms 内のブレストファイルの「結論」セクションで管理
- 横断確認したい場合はAIにブレスト結論を一覧化させる

### トレーサビリティ（選択式オプション）

「トレーサビリティ」オプションを選択したプロジェクトでのみ使用する。成果物間の対応関係を `traceability-matrix.md` で管理する。

| 要件ID | 要件概要 | 設計書 | 設計箇所 | 製造計画書 | コードファイル | テスト仕様 | テスト結果 | 状態 |

成果物を変更する際は「変更影響マトリクス」を参照し、影響を受ける成果物を提示する。要件書への項目追加時は `R-XXX`（連番）のIDを自動付与する。

### 監査・コンプライアンス（選択式オプション）

「監査」オプションを選択したプロジェクトでのみ適用する。

- 各スキル実行時に監査証跡（実行日時・スキル名・対象・参照仕様・結果・承認記録）を生成する
- コンプライアンス台帳で品質要件と品質ゲートを管理する
- 各フェーズ完了時に品質ゲートの通過を確認する

## Office ファイル読み込みルール

Office形式（.docx / .pptx / .xlsx）を参照する場合、Markdownに変換してから読み込む。**コマンドは OS によって読み替える**（[クロスプラットフォーム](#クロスプラットフォーム)参照）。

| 拡張子 | 変換コマンド（POSIX / Windows） | 必要ツール |
|---|---|---|
| .docx | `pandoc "<file>" -t markdown -o "<output>.md"`（pandoc未導入時は下記スクリプト） | pandoc |
| .docx | `python3 .aide/templates/export/scripts/docx2md.py "<file>"` / Windows: `python ...` または `py ...` | python-docx 等 |
| .pptx | `python3 .aide/templates/export/scripts/pptx2md.py "<file>"` / Windows: `python ...` | python-pptx |
| .xlsx | `python3 .aide/templates/export/scripts/xlsx2md.py "<file>"` / Windows: `python ...` | openpyxl |

**運用ルール:**
- 変換後のMDは元ファイルと同じディレクトリに `<元ファイル名>.md` として出力
- 変換済みMDが元ファイルより新しい場合は再変換しない
- 画像は `<元ファイル名>_images/` に抽出
- 変換結果は参考用。正式な成果物はMDで再作成する
- 必要パッケージは `.aide/templates/export/scripts/requirements-import.txt` を参照

## スキル・エージェント定義の保守

スキル定義は `.aide/skills/<skill-name>/SKILL.md`、エージェント定義は `.aide/agents/<agent-name>.md` が **Single Source of Truth**。各AIツール向けのラッパーは sync スクリプトで自動生成する。

**運用ルール:**
- 正本（`.aide/skills/` / `.aide/agents/`）のみを編集する。各ツール向けラッパーは直接編集しない（sync で上書きされる）
- プロジェクト独自のスキル・エージェントは `.aide/` の外（`.claude/skills/`・`.agents/skills/`・`.claude/agents/`）に直接置く（[カスタマイズ](#カスタマイズ)）。sync 対象外のため消えない
- 編集後は sync を実行して全ラッパーを再同期する:

```bash
# POSIX（bash）
bash .aide/scripts/sync-skills.sh            # 全ツール向けに生成
bash .aide/scripts/sync-skills.sh claude     # Claude Code のみ
bash .aide/scripts/sync-skills.sh agents     # Copilot + Codex（.agents/）のみ
```

```powershell
# Windows（PowerShell, WSL2 不要）
pwsh -File .aide/scripts/sync-skills.ps1            # 全ツール向けに生成
pwsh -File .aide/scripts/sync-skills.ps1 claude
pwsh -File .aide/scripts/sync-skills.ps1 agents
```

**フロントマターの規約:**

| フィールド | 用途 | 必須 |
|---|---|---|
| `name` | スキル識別子（親ディレクトリ名と一致させる） | ✓ |
| `description` | 長文トリガー（`.aide/skills/` のみ）。発火条件を自然言語で詳細に記述 | ✓ |
| `short_description` | 短文ラベル（ラッパーが参照）。1〜2文 | 推奨 |

`short_description` が無い場合、sync はラッパーの `description` に正本の `description` を流用する。

## マルチツール集約

aide が対応するツールは Claude Code / GitHub Copilot / Codex CLI。**ルールファイルは CLAUDE.md と AGENTS.md の2本のみ**、**スキルラッパー出力先は `.claude/skills/` と `.agents/skills/` の2系統のみ**に集約する。

| ツール | ルールファイル | スキルラッパー | エージェント |
|---|---|---|---|
| Claude Code | CLAUDE.md | `.claude/skills/` | `.claude/agents/` |
| GitHub Copilot | AGENTS.md | `.agents/skills/` | （`.agents/` 規約に展開） |
| Codex CLI | AGENTS.md | `.agents/skills/` | （`.agents/` 規約に展開） |

- GitHub Copilot は AGENTS.md（ルートで一次命令）と `.agents/skills/`（横断オープン標準）を解釈するため、Codex と同一規約に集約する
- `.github/copilot-instructions.md` / `.github/skills/` / `.github/prompts/` は **使用しない**

## クロスプラットフォーム

aide は Windows 11 / PowerShell（WSL2 なし）でも動作する。

- **sync は2本併設**: `sync-skills.sh`（bash）と `sync-skills.ps1`（PowerShell ネイティブ）。両者は同一出力（2系統ラッパー＋エージェント展開）を生成する
- **AI 実行コマンドの OS 対応**:
  - Python 実行: POSIX `python3` / Windows `python` または `py`
  - sync 実行: POSIX `bash .aide/scripts/sync-skills.sh` / Windows `pwsh -File .aide/scripts/sync-skills.ps1`
  - `pandoc` および変換 Python スクリプトはクロスプラットフォーム（呼び出しコマンド名のみ OS 依存）
- パスは可能な限り相対パス・スラッシュ区切りで記述する

## 管理系情報の配置ルール

見積・スケジュール・タスク・優先度・担当・ステータスなどの管理系情報は、成果物（要件書・設計書・製造計画書）には含めない。すべて作業フォルダ内の管理領域で一元管理する。

設計フェーズ以降の見積変更は「計画修正」として扱い、利用者の明示的な許可なく変更しない。
